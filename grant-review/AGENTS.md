# Grant Review Project Instructions

## Deployment

- Grant Review is an IIS child application at `/apps/grant-review` mapped to `E:\apps\grant-review\public`.
- Keep `APP_URL` set to the full public `/apps/grant-review` URL in production.
- Tests override `APP_URL` with `http://localhost` so route tests are independent of the IIS subpath.
- Frontend assets are compiled (`@vite` manifest in `public/build`, gitignored) — after adding new Tailwind classes or changing `resources/css|js`, run `npm run build` in `grant-review` or new styles silently no-op (no `npm run dev` watcher runs during local testing).
- Regenerate the Grant Review favicon with `php E:/apps/grant-review/scripts/generate-favicon.php` (requires GD); it rasterizes the heroicons v2 outline `trophy` logo (the mark shown in every page header) white on the red rounded square and writes `public/favicon.png` + `public/favicon.ico` (replacing the old 0-byte scaffold `favicon.ico`). The `scripts/` directory lives outside `public/`, so it is never web-accessible.

## UHPH App Hub SSO

Hub SSO is the production configuration — the approved cutover completed on 2026-10-07 and production now runs `HUB_SSO_ENABLED=true` against the real Hub with the legacy local login replaced by Hub sign-in and Hub-managed passwords. It is switched per environment by `HUB_SSO_ENABLED` in Grant Review's ignored `.env` (see `docs/local-authentication-setup.md` for full local setup):

```dotenv
HUB_SSO_ENABLED=true
HUB_URL=https://uhph.uh.edu/apps
HUB_CLIENT_ID=
HUB_CLIENT_SECRET=
HUB_CALLBACK_URI=/apps/grant-review/auth/hub/callback
HUB_VERIFY_TLS=true
HUB_SESSION_REVALIDATION_MINUTES=15
EMERGENCY_LOGIN_ENABLED=false
EMERGENCY_LOGIN_ALLOWED_IPS=
```

`HUB_SSO_ENABLED` is Grant Review's own boolean switch, independent of the Hub's `HUB_LOGIN_MODE` (`local`, `sso`, or `hybrid`, set only in the app-hub `.env` — see `app-hub/AGENTS.md` → "Login modes"), which selects which sign-in methods the Hub itself offers. `.env` is per-deployment and ignored, like `bootstrap/cache` config caches and `public/build`: git moves code and docs only, so each environment keeps its own values — never change config defaults to push production settings onto local, never copy production secrets into a local `.env`, and never set `HUB_VERIFY_TLS=false` as a workaround (production additionally requires every Hub URL to be HTTPS).

Keeping `HUB_SSO_ENABLED=false` locally exercises only the legacy Grant Review local login; it does not test centralized sign-in or coordinated logout. To test SSO locally, set `HUB_SSO_ENABLED=true` with an environment-specific `HUB_URL` (e.g. `http://localhost:8000/apps`), locally generated Hub credentials, and a `HUB_CALLBACK_URI` matching the local Hub application registration exactly — while leaving the production deployment unchanged.

Activation procedure:

1. Generate or rotate Grant Review credentials in the UHPH App Hub application editor for that environment.
2. Copy the one-time client ID and secret into Grant Review's ignored `.env`.
3. Set that environment's `HUB_URL` (`https://uhph.uh.edu/apps` in production) and keep `HUB_CALLBACK_URI` identical to the registered internal `/apps/...` path.
4. Configure a restricted administrator IP allowlist if emergency login is required.
5. Confirm the Hub registration and that each account holds a Grant Review assignment before enabling — the acceptance round trip cannot run until the integration is on.
6. Set `HUB_SSO_ENABLED=true`.
7. Clear the changed app's config cache: `composer exec --working-dir="E:/apps/grant-review" -- php artisan config:clear` (from an elevated shell if IIS file permissions block cache replacement). `.env` changes require no `npm run build`.
8. Run the acceptance checks in a browser: a fresh SSO sign-in through the Hub and a coordinated global-logout round trip.

Never commit or log `HUB_CLIENT_SECRET`. Hub credentials and legacy local passwords are independent stores: mapping a Hub identity onto a local profile preserves the existing `password_hash` for every role during the transition (hashes already cleared by earlier releases are not restored by rolling back), so never "sync" passwords to fix a sign-in problem. Diagnose failures by status and endpoint: a 403 during Hub authorization can indicate a missing or revoked Grant Review assignment, while a 403 from the scoped managed-users API can indicate a rejected actor token — check which endpoint failed before fixing anything; a 502 during the callback can indicate an exchange, connectivity, or Hub response-validation failure (check `HUB_URL`, credentials, callback match, and TLS). The normal `/login` route uses local authentication while SSO is disabled and redirects to the Hub when enabled. Hub sessions are forced through authorization again every 15 minutes by default so access revocations and role changes take effect. The emergency route is `/emergency-login` and only accepts active Grant Review administrators from configured IP addresses. Legacy set-password invitations and local role/status editing are disabled while Hub SSO is active. User onboarding goes through the scoped Hub managed-users API: single invites and the CSV bulk import on `admin/users/create` (submitter role + round invitation per row; each row calls the Hub API, so failures are reported per row rather than all-or-nothing — a CSV row never demotes an existing reviewer/admin). Bulk multi-role onboarding remains in the Hub at `/apps/admin/users/import`. Grant Review continues to manage local profile fields and round invitations after provisioning.

The SSO callback stores the Hub-issued application count, signed logout URL, and short-lived encrypted actor token in the local session. When periodic Hub session revalidation expires, the shared client middleware must preserve the requested named-route URL in `url.intended` before invalidating the local session so SSO returns users to deep links rather than their role dashboard. “All applications” appears only for users assigned to multiple enabled Hub apps and returns to the launcher without ending either session. “Sign out” destroys the Grant Review session and follows the trusted signed Hub logout URL. The Hub then sends the browser through each registered front-channel endpoint; `/auth/hub/logout` validates the opaque transaction with the Hub before clearing Grant Review, so signing out anywhere immediately clears all application and Hub sessions before showing the contextual login screen. `/auth/hub/logout` returns 404 whenever `hub.enabled` is false; that dead-end no longer affects production because the endpoint is live under `HUB_SSO_ENABLED=true` — but the same 404 applies to any other environment that disables the flag while the endpoint stays registered. The logout transaction is single-use and expires after two minutes; an expired logout URL cannot be reused — sign out again for a fresh one. Never construct or accept an arbitrary logout URL.

Grant Review application administrators may create identities and change Grant Review roles from `/apps/grant-review/admin/users`. Grant Review sends both its application credentials and the current actor token to the Hub's scoped management endpoint, then upserts the confirmed identity into its local profile database. Application administrators may assign `admin`, `submitter`, or `reviewer` only for Grant Review; they cannot grant global Hub administration, affect another application, disable/delete the central identity, or remove their own Grant Review administrator role. New identities receive a UHPH App Hub invitation whose content follows the Hub's `HUB_LOGIN_MODE` — CougarNet-only instructions in `sso`, a set-password link in `local`, or CougarNet plus an optional Hub-local password setup link in `hybrid`. Grant Review always signs users in through the Hub (it never authenticates through both methods itself); the authoritative `login_mode` arrives in the Hub identity response, is stored in the local session as `hub_login_mode`, and drives the onboarding copy on the admin workflow chart and the `invitation-hub` email preview after the next Hub authorization or revalidation — at most `HUB_SESSION_REVALIDATION_MINUTES` unless the user signs out and back in. After SSO, authenticated users with incomplete local profiles are restricted to `/complete-profile` until they provide phone, department, title, a 7–20 digit PeopleSoft ID, and investigator type (`pi` or `other`); early-stage and new-investigator flags are captured independently. Local profile fields and round invitations remain in Grant Review.

While Hub SSO is enabled, UHPH App Hub is authoritative for account deletion and application-access revocation. Opening Grant Review's Users page reconciles the complete authoritative Grant Review assignment list from the Hub: missing profiles are provisioned, role changes are applied, and local profiles absent from the Hub list are marked disabled and moved to Archived Users. Application admins may use “Revoke Access” to remove only the Grant Review assignment through the scoped Hub API. Never physically delete an SSO profile during revocation because submissions, reviews, decisions, and round history reference it; local deletion remains available only when Hub SSO is disabled.

Reconciled profiles distinguish **access** from **onboarding**: `HubIdentityService::resolve($identity, $authenticated)` marks a profile `active` only for a real authenticated callback (`$authenticated=true`, the default) or when the managed-users response reports `onboarding_pending=false`. A management-side sync (`false`) keeps a pending Hub identity `invited` — including profiles earlier corrupted to `active` — so the Users page shows the existing “Invited” badge until the user completes Hub password setup or signs in, and legacy `invite_token_hash`/`invite_expires_at` are cleared only when the resulting status is `active`. Responses from an older Hub without the optional flag preserve an existing `invited` status and otherwise act as before. The index lists `active` **and** `invited` profiles together; Archived Users shows `disabled` only.

Reviewer workflow: admins first invite active reviewers to declare COI for a round (`/apps/grant-review/admin/review-invitations`, labeled "COI invitations", table `reviewer_round_invitations`), which emails a conflict-of-interest invitation. The declaration form requires two attestations before submission: the Confidentiality Statement & Code of Conduct and the COI Policy & Guidelines (each a required checkbox with the full document in a modal). Each accepted confidentiality checkbox records a `confidentiality_agreements` row per reviewer + cycle + document version (canonical text and version live in `App\Support\ConfidentialityAgreementDocument`; the stored `content` snapshot is rendered from the same source) — resubmissions with the same version keep the original timestamp, and admins see the record on the user profile page. The COI Policy & Guidelines work the same way per declaration: canonical wording and the NIH link live in `App\Support\ConflictOfInterestPolicyDocument`, each declaration stores `coi_policy_version`/`coi_policy_content`/`coi_policy_acknowledged_at` (same instant as `declared_at`), and the form posts a `coi_policy_digest` of version + text so submissions opened before a wording change are rejected — legacy declarations have `NULL` snapshots and are shown as "not recorded", never assumed to match current wording. Reviewers declare per-proposal responses (`conflict_of_interest_responses`, one explicit `clear` or `potential_conflict` row per screened proposal) before any assignment; each resubmission supersedes the previous declaration version (history preserved via `superseded_at`). Declarations are matched by reviewer+round, so legacy declarations without invitation linkage still count as coverage. COI status is visible at `/apps/grant-review/admin/conflicts` (including awaiting-declaration invitations) with an "Assign reviews" shortcut, and as per-proposal badges on the assignment page. Each submitted row links "View declaration history" to `admin/conflicts/{declaration}`, which lists every declaration version (newest first) with its declared/superseded/notification timestamps, recorded policy version and accepted text, and screening detail per proposal. Reported conflicts are advisory: the server only requires an active invitation for newly assigned reviewers; assigning a reviewer with a reported conflict triggers a confirmation dialog, and the decision remains the administrator's. Assignment of uninvited reviewers is rejected server-side. COI submissions notify all active Grant Review administrators through the configured mailer (delivery recorded in `admin_notified_at`; reviewer messaging only claims notification when delivery succeeded); the default UH deployment uses `post-office.uh.edu:25` from `donotreply@uh.edu`. Backfill legacy data with `php artisan reviewer-screening:backfill` (run `--dry-run` first); the legacy `conflict_of_interest_entries` table is retained read-only during the transition.

The reusable Laravel protocol client is the local Composer package `uh/app-hub-client` at `E:\apps\packages\laravel-app-hub-client`. Keep authorization-code exchange, Hub response validation, session lifecycle, and Hub middleware in that package. Keep Grant Review user mapping and role-specific destinations behind `MapsHubIdentity` and `DeterminesLoginDestination` implementations in this application.
